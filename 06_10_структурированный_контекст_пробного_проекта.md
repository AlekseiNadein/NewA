# 06.10 — структурированный контекст по пробному проекту

Источник: транскрибация разговора `06_10_Планирование_разработки_SaaS_платформы_и_обучение_с_использованием.txt`.

Задача документа: собрать весь контекст, который в разговоре относится к разработке пробного/тестового проекта, его смыслу, предполагаемой архитектуре, предметной области, учебным целям и способу работы с AI-инструментами.

## 1. Зачем вообще нужен пробный проект

В начале обсуждения зафиксировали, что до этого изучение шло через отдельные технические эксперименты: REST API, очереди, воркеры, Docker/Kubernetes и т.д. При этом спикеры подчеркнули, что без цельной прикладной задачи знания остаются разрозненными: понятно, что технология работает, но неясно, где и зачем ее применять.

Главная мысль: нужен проект, который будет не учебным набором абстрактных примеров, а задачей из понятной реальной области. Тогда появится практический смысл, интерес и необходимость принимать архитектурные решения.

Отдельно проговорили, что слишком маленькая задача не подходит. Telegram-бот был приведен как пример слишком простой задачи: с современными AI-инструментами он делается очень быстро и не даст достаточной глубины.

## 2. Что уже было попробовано до выбора проекта

Участник уже успел потрогать несколько технических блоков:

- Простейший REST API: сервер слушает запросы, умеет обрабатывать `GET` и `POST`.
- Подключение API к базе данных или хранилищу. В транскрибации это место распознано нечетко как «подгрызке», поэтому точный термин нужно перепроверить по контексту.
- Очереди: сначала была попытка сделать свою очередь, затем по совету была использована официальная очередь/библиотека.
- AMQP/RabbitMQ: в транскрибации звучит как «АМНП» и «ради», но по контексту речь, вероятно, об AMQP и RabbitMQ.
- Воркеры на Go:
  - запуск и завершение горутин;
  - синхронизация;
  - отслеживание завершения;
  - `Mutex` для случаев, когда несколько горутин пишут в одно место;
  - каналы;
  - регулирование количества воркеров и наблюдение за тем, как меняется обработка.
- K3s:
  - развернут на Ubuntu в виртуальной среде;
  - рассматривался вместе с Docker;
  - Kubernetes видел Docker-контейнеры и управлял их запуском/остановкой.

Вывод спикеров: технических кусочков уже набралось достаточно, но их надо применить в связной задаче.

## 3. Первый опыт с Cursor и попытка переписывания существующего сервиса

Участник установил trial-версию Cursor и быстро проверил его на тестовой задаче. Результат впечатлил: задачу удалось записать/сформулировать, Cursor быстро сгенерировал код, и это выглядело полезно.

После этого был взят существующий рабочий проект — сервер лицензий:

- сервер лицензий устанавливается на Windows Server;
- у него есть SDK для работы с аппаратным ключом;
- есть SDK для работы с наложенной защитой;
- участник попробовал «натравить» Cursor на проект и попросить переписать его на Go;
- Cursor сначала начал работать бодро, но быстро уперся в лимиты/объемы запросов trial-версии.

Эта попытка стала одним из кандидатов на пробный проект: переписать или переосмыслить сервер лицензий так, чтобы он мог работать не только в Windows-среде.

## 4. Обсужденные кандидаты на основу пробного проекта

### 4.1. Сервер лицензий под Linux / сетевое решение

Участник предложил докрутить сервис лицензий, потому что это реальный рабочий контекст. Идея:

- сейчас сервер лицензий связан с Windows;
- потенциально могут быть клиенты, у которых вообще нет Windows;
- могут быть заказчики на государственных или специфичных ОС;
- нужно иметь возможность предложить им сетевое решение;
- в текущей сетевой реализации уже есть сервер лицензий, клиенты и права;
- сервер может стоять как в локальной сети, так и за ее пределами, с обращением из другой подсети.

Важно: в разговоре уточнили, что текущий сервер лицензий — это именно сервер для лицензирования, а не полноценный сервер данных продукта.

### 4.2. Перенос PDF/нормативных материалов с FTP

Обсуждалась недавняя задача по уменьшению дистрибутива:

- в поставке было около 1.2 ГБ;
- примерно 700 МБ занимали нормативные PDF-файлы;
- не все PDF нужны каждому пользователю;
- PDF вынесли из каждой версии на общий уровень;
- если они скачаны один раз, то становятся доступны следующим версиям;
- технически скачивание идет через FTP.

Один из спикеров отметил, что FTP — плохое/устаревающее решение, и можно было бы заменить FTP. Но эту задачу сочли маленькой, то есть недостаточно глубокой для основного пробного проекта.

### 4.3. Повторить часть продукта как SaaS-сервис

Итоговое направление, к которому пришли: взять понятный рабочий контекст и попробовать переосмыслить продукт как SaaS-платформу.

Суть: не просто переписать один сервис, а собрать основу SaaS-платформы для продукта:

- есть frontend;
- есть backend;
- есть база данных;
- есть отдельный сервис/модуль аккаунтов для аутентификации и авторизации;
- есть компании;
- внутри компаний есть пользователи;
- у пользователей есть права;
- есть небольшой, но реальный кусок функциональности продукта;
- все это должно работать через браузер.

Спикеры описали это как более интересную и полезную задачу, чем маленькие утилиты, потому что она заставит думать об архитектуре, правах, структуре данных, сервисах и границах ответственности.

## 5. Итоговая формулировка пробного проекта

Пробный проект: сделать MVP SaaS-платформы на основе предметной области существующего продукта.

Минимальная целевая схема:

- Пользователь открывает веб-интерфейс в браузере.
- Проходит авторизацию.
- Авторизация выполняется через отдельный сервис аккаунтов/пользователей.
- После входа пользователь попадает в пользовательский интерфейс.
- Данные хранятся в базе на сервере.
- Через UI можно работать с частью предметной модели продукта.
- Должны быть базовые CRUD-операции:
  - создание;
  - чтение/получение;
  - редактирование;
  - удаление, если оно уместно для выбранной сущности.

Основной фокус обучения — backend, но frontend тоже нужно сделать, чтобы получить опыт создания полного приложения и видеть результат в браузере.

## 6. Предполагаемая структура репозитория и компонентов

В разговоре прозвучало, что внутри одного проекта/репозитория должны быть отдельно backend и frontend. Формулировка в транскрибации звучит как «одна репа с бэкэндом, одна с фронтэндом», но по контексту это можно трактовать как монорепозиторий с двумя частями или два отдельных подпроекта.

Предполагаемые компоненты:

- `frontend` — веб-интерфейс:
  - экран логина;
  - пользовательский интерфейс после авторизации;
  - административный интерфейс для управления компаниями/пользователями/правами;
  - интерфейс для выбранной предметной функциональности.
- `backend` — основной API:
  - работа с предметными сущностями;
  - CRUD;
  - бизнес-логика;
  - обращение к базе данных;
  - публикация событий в очередь, если выбранный сценарий это требует.
- `auth/account service` — сервис аккаунтов:
  - аутентификация;
  - авторизация;
  - выдача JWT-токенов;
  - хранение пользователей;
  - хранение прав;
  - привязка пользователей к компаниям.
- `database` — серверная база данных:
  - компании;
  - пользователи;
  - права;
  - предметные сущности;
  - при необходимости журналы/реестры.
- `queue/workers` — асинхронная обработка:
  - пересчет аналитики;
  - отправка уведомлений;
  - фоновые задачи.

## 7. Аутентификация и авторизация

Один из обязательных учебных блоков — разобраться, как работают аутентификация и авторизация.

Требования, которые прозвучали:

- сделать отдельный сервис, отвечающий за аутентификацию и авторизацию;
- использовать JWT-токены;
- понять, что такое JWT и как он применяется;
- хранить пользователей и права в этом сервисе;
- после входа frontend должен получать доступ к пользовательскому интерфейсу на основании авторизации;
- сделать отдельный административный интерфейс.

В разговоре JWT распознано как «джиуэйтэй» или «JVT», но по смыслу речь именно о JWT.

## 8. Компании, пользователи и права

В SaaS-модели вместо выдачи отдельного пользователя или локального сервера лицензий предлагается создавать компании.

Модель, которую обсуждали:

- можно создать компанию;
- внутри компании можно создать `N` пользователей продукта;
- все пользователи хранятся централизованно;
- права пользователей тоже хранятся централизованно;
- пользователь может иметь определенный уровень доступа;
- административная панель должна позволять управлять этой структурой.

Права обсуждались как важная часть пробного проекта:

- может быть супер-администратор;
- может быть обычный пользователь;
- у разных пользователей могут быть разные права на разные справочники или сущности;
- где-то пользователь может только читать;
- где-то может читать и изменять;
- где-то может создавать/удалять;
- права могут быть завязаны на роль пользователя в компании.

Из существующего продукта был приведен пример прав на установку/обновление нормативных данных:

- пользователь может иметь право дополнить нормативные данные;
- пользователь может иметь право установить новую версию нормативных данных;
- такие права могут быть у администратора или начальника сметного отдела;
- эти права сейчас работают в сетевой реализации.

## 9. Предметная область для функционального модуля

Спикеры предлагали взять не абстрактный справочник, а кусок, близкий к реальной жизни и существующему продукту.

Примеры простых сущностей:

- справочники;
- товары;
- сделки;
- нормативные данные;
- пользовательские данные.

Но отдельно подчеркнули: простой CRUD над одним справочником может быть слишком поверхностным. Лучше выбрать более сложную сущность, где появятся вложенные данные, статусы и связанные операции.

Пример сложной сущности из разговора — сделка:

- у сделки есть статусы;
- к сделке привязываются контрагенты;
- у сделки есть оплаты;
- оплаты могут попадать в отдельный реестр оплат;
- в сделку добавляются товары;
- товары можно убирать;
- у товаров внутри сделки можно менять цену;
- изменение сделки может порождать связанные записи в других таблицах/реестрах.

Пример из предметной области участника — смета:

- есть нормативные данные, которые в целом консервативны;
- есть данные пользователя;
- есть СМЕТ/смета;
- внутри сметы есть позиции;
- есть ресурсы;
- ресурсы входят в состав отдельных работ;
- пользователь сам создает часть позиций или данных.

Вывод: для пробного проекта нужно выбрать маленький, но содержательный фрагмент этой модели. Он должен быть достаточно сложным, чтобы потребовалось продумать архитектуру, связи сущностей, права и асинхронные процессы.

## 10. CRUD как базовый слой

CRUD был обозначен как базовый минимум почти любого приложения:

- добавить элемент;
- получить элементы;
- отредактировать элемент;
- удалить элемент, если доменная модель это допускает.

Отдельно отмечено, что 80-90% операций многих приложений сводятся к созданию, получению и изменению данных. Поэтому CRUD нужен как базовая практическая основа, но желательно не ограничиваться тривиальным справочником.

## 11. Очереди и воркеры в проекте

Очереди предложены как практический способ применить уже изученные темы.

Обсужденные сценарии:

- Изменился товар или другая сущность.
- Основной сервис быстро сохраняет изменение в справочнике/таблице.
- Вместо того чтобы сразу делать тяжелую дополнительную работу, сервис кладет событие в очередь.
- Отдельный воркер слушает очередь.
- Воркер получает событие и выполняет фоновую задачу.

Примеры фоновых задач:

- пересчитать аналитику;
- обновить статистику продаж за месяц;
- пересчитать карточки/агрегаты;
- отправить пользователю уведомление;
- сообщить, что платеж пришел;
- сообщить, что сделка оплачена.

Также обсуждался отдельный сервис-нотификатор:

- основной сервис не должен разрастаться отправкой писем/Telegram-сообщений;
- он только публикует событие в очередь;
- маленький сервис-нотификатор получает событие;
- сервис-нотификатор отправляет email или сообщение в Telegram.

Смысл такого подхода: разгрузить основной сервис, разделить ответственность и показать практическую пользу очередей.

## 12. Frontend и возможное будущее с desktop

Хотя основной фокус участника — backend, frontend предложили включить обязательно:

- он даст опыт полного цикла разработки;
- позволит работать с приложением через браузер;
- поможет лучше понимать взаимодействие UI, API, авторизации и прав;
- даст видимый результат.

Также был упомянут возможный будущий путь: если нужен desktop-интерфейс, веб-приложение можно обернуть в Electron.

Идеи на будущее с Electron:

- приложение выглядит как desktop;
- часть функциональности может работать без интернета;
- можно сделать локальное кэширование;
- можно синхронизировать данные при появлении сети.

Это обсуждалось как потенциальное направление на будущее, а не как обязательная часть текущего MVP.

## 13. Подписка/лицензирование как будущий слой

В разговоре прозвучало, что создание компаний и пользователей внутри компаний может заменить текущую модель с сервером лицензий как основу SaaS-платформы.

Также упоминалось, что позже можно показать, как сделать подписку. Но подписка не была подробно разложена как обязательная часть первой реализации. Это скорее следующий этап после базовой платформы:

- компания как единица владения/клиент;
- пользователи внутри компании;
- права внутри компании;
- в будущем — подписка/тариф/доступ.

## 14. Как предлагается работать с AI-инструментами

Очень важный блок разговора — не только что делать, но и как делать.

Подход:

- не просто отдавать AI задачу на реализацию;
- сначала формулировать задачу;
- просить AI предложить 2-3 варианта реализации;
- просить объяснить плюсы и минусы каждого варианта;
- выбирать подходящий вариант;
- после выбора отдавать реализацию по частям;
- проверять, что AI не делает неадекватных решений;
- валидировать архитектуру и код;
- учиться через диалог с AI.

Роль участника в этом процессе:

- проектировать архитектуру;
- ставить задачи AI;
- обсуждать решения;
- оценивать варианты;
- проверять качество результата;
- не принимать сгенерированный код вслепую.

Один из спикеров отдельно подчеркнул, что полезно использовать режим планирования: сначала получить план, отредактировать его, понять и только потом переходить к реализации.

Также обсуждалась практическая работа с AI через голос и визуальный контекст:

- можно не только писать задачи, но и наговаривать их голосом;
- для визуальной части можно открыть страницу, записать комментарии и попросить AI передвинуть элементы, добавить кнопки, фильтры, изменить цвет и т.д.;
- для backend можно открыть базу или структуру данных и объяснить, какие поля, типы или связи нужно поменять;
- AI может смотреть сделанные изменения, коммиты и части проекта, после чего задачу можно дорабатывать итерационно;
- такой формат ускоряет не только написание кода, но и обсуждение архитектурных решений.

## 15. Использование записи и артефактов разговора

Спикеры обсуждали, что запись разговора и фото схемы можно использовать как входной контекст для AI:

- отправить фото схемы;
- отправить транскрибацию записи;
- попросить AI обсудить, как двигаться к реализации;
- на основе разговора составить план проекта;
- затем идти по плану частями.

Это прямо связано с текущей задачей: структурированный документ из транскрибации может стать исходным контекстом для Cursor/Codex при планировании проекта.

## 16. Обучающий смысл проекта

Проект нужен не только как технический результат, но и как способ научиться учиться с AI.

Обсужденные учебные цели:

- научиться собирать реальную задачу из нескольких технологий;
- разобраться с авторизацией, аутентификацией и JWT;
- потренироваться проектировать backend;
- получить опыт frontend-разработки;
- применить очереди и воркеры не абстрактно, а в бизнес-сценариях;
- понять границы сервисов;
- научиться валидировать архитектурные решения AI;
- быстрее изучать новые технологии через диалог, а не через долгий самостоятельный поиск по документации.

Пример учебного взаимодействия с AI:

- «Хочу разобраться, как выстроить авторизацию и валидацию токена».
- «Какие есть подходы?»
- «Какие лучшие практики?»
- «Какие подводные камни?»
- «Как делать и как не делать?»
- «Объясни проще / на пальцах».

## 17. Инструменты: Cursor, Codex и подписки

После технического обсуждения спикеры перешли к выбору инструмента и подписки.

Что обсуждалось:

- Cursor уже был установлен в trial-версии.
- Trial быстро показал пользу, но лимиты быстро закончились.
- Codex/OpenAI обсуждался как альтернативный или дополнительный инструмент.
- У Codex обсуждалась более удобная модель лимитов по неделям/периодам.
- У Cursor отмечались месячные лимиты.
- Для старта решили, что Cursor будет более привычным и оптимальным.
- Также обсуждалась возможная подписка примерно на 20 долларов с возможностью апгрейда.

Практическая часть с виртуальной картой, VPN, Google Authenticator и оплатой подписки относится к обеспечению доступа к инструменту, но не добавляет новых требований к архитектуре пробного проекта.

## 18. Что не является обязательной частью MVP

Чтобы не смешивать основной пробный проект с будущими идеями, важно отделить обязательное от дополнительного.

Не выглядит обязательным для первой версии:

- полноценное переписывание всего существующего продукта;
- полная замена текущего сервера лицензий;
- полноценная подписочная биллинговая система;
- Electron/Desktop-версия;
- offline-first режим;
- полная модель всех сметных данных;
- замена FTP как отдельная задача;
- production-ready Kubernetes/K3s-деплой.

Эти темы полезны как контекст и возможные следующие шаги, но MVP должен быть уже и управляемее.

## 19. Возможный состав MVP по итогам разговора

Наиболее точная формулировка MVP, вытекающая из обсуждения:

1. Сделать web-приложение в формате SaaS.
2. Реализовать backend API.
3. Реализовать frontend.
4. Подключить серверную базу данных.
5. Сделать сервис аккаунтов:
   - регистрация/создание пользователей;
   - логин;
   - JWT;
   - хранение прав;
   - привязка к компаниям.
6. Сделать административный интерфейс:
   - создание компании;
   - создание пользователей внутри компании;
   - назначение прав.
7. Сделать небольшой предметный модуль:
   - лучше не простой справочник, а сущность со связями;
   - возможные варианты: смета, позиции сметы, ресурсы, пользовательские позиции, либо аналог сделки с позициями/статусами/оплатами.
8. Реализовать CRUD для выбранных сущностей.
9. Реализовать проверку прав на операции.
10. Добавить очередь и воркер для одного практического сценария:
    - пересчет аналитики;
    - уведомление;
    - обработка события изменения сущности.
11. Оформить проект так, чтобы его можно было развивать дальше:
    - подписки;
    - desktop/Electron;
    - более сложная предметная модель;
    - Kubernetes/K3s-деплой.

## 20. Открытые вопросы, которые остались после разговора

Нужно уточнить перед началом разработки:

- Какой именно предметный кусок выбрать для MVP:
  - сметы/позиции/ресурсы;
  - сделки/товары/оплаты;
  - лицензии/компании/пользователи;
  - гибридная учебная модель.
- Нужно ли делать отдельный auth-service физически отдельным сервисом или достаточно отдельного модуля внутри backend на первом этапе.
- Какая база данных будет использоваться.
- Какой frontend-стек выбрать.
- Какая очередь будет использоваться: RabbitMQ/AMQP или другой вариант.
- Нужен ли Docker Compose для локального запуска.
- Нужно ли сразу поднимать это в K3s или оставить K3s как отдельный следующий этап.
- Какой уровень детализации прав нужен в MVP:
  - роли;
  - permissions;
  - права на сущности;
  - права на действия.
- Нужно ли реализовывать удаление физически или использовать мягкое удаление/статусы, как в реальных системах.
- Как именно связать SaaS-компании с будущей подпиской/лицензированием.

## 21. Короткий итог

Спикеры пришли к тому, что пробный проект должен быть не маленькой демонстрацией, а учебным MVP SaaS-платформы на понятном рабочем контексте. В нем нужно соединить backend, frontend, базу данных, JWT-аутентификацию, авторизацию, компании, пользователей, права, CRUD по предметным сущностям и хотя бы один практический сценарий с очередью/воркером.

Главная цель — не просто написать код, а научиться проектировать систему вместе с AI: обсуждать варианты, выбирать архитектуру, ставить задачи по частям, проверять результат и использовать проект как практическую основу для обучения.
